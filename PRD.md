# Overview
I want to build an Android mobile app that will allow Scouting America scouts to track and record their progress in earning merit badges. 

# Key User Journeys
- On first app launch the user should be prompted for their name and unit number.
- The user should be able to change their name and unit number later.
- On subsequent app launches the user should land on a home page that displays their name and a summary of their merit badge progress.
- A user should be able to browse a list of all current Scouting America merit badges.
- A user should be able to search for a specific merit badge by name or description.
- When a merit badge is selected the user should be given a page that briefly describes the merit badge and allows the user to record their progress towards completion.
  - This page should begin with a brief description of the merit badge and any relevant information, such as whether it is eagle required.
  - This page should give the user the ability to enter their merit badge counselor's name and contact information.
  - This page should give the user a brief description of each requirement for the merit badge as well as the ability to record all relevant data necessary to satisfy the progress against that requirement.
  - This page should be easy to navigate on a mobile device, and the user should be able to understand the full set of requirements without extensive scrolling. If any part of the merit badge requires large trackers or detailed information the user should have the option to click into a sub-page for those requirements.
  - Where possible, the brief descriptions of requirements should link to the full, official, Scouting America documentation for the relevant requirement.
  - When recording progress on a merit badge requirement the user should have the option to include a date on which the requirement was completed.
  - When recording progress on a merit badge the user should have the option to add notes about that requirement.
  - When a merit badge is completed the user should have the ability to generate a report in PDF format that reflects the entirety of the data they have recorded for that merit badge, and to save and/or share that report with standard Android save and share features.
  - This page should allow the user to mark a merit badge as completed on a prior date without entering specific data for each requirement.
  - Scouting America updates merit badge requirements over time, usually each January 1. By default, a merit badge should use the newest version of its requirements.
  - The user should be able to select the previous version of a merit badge's requirements instead, when the app has one, for example if they started working on the badge before a change.
  - The first release of the app includes only each merit badge's current requirements. From then on, the app keeps every version of the requirements it has shipped, so existing users can keep working on the version they started.
  - When an app update brings newer requirements for a merit badge the user has already started, the badge should stay on the version the user was using, so their recorded progress still matches its requirements. The user should be able to switch that badge to the newest version themselves.
- A user should be able to track and record their progress toward each Scouts BSA rank, Scout through Eagle, as they do for merit badges.
- A user should have the option to clear all merit badge data, all progress for a specific merit badge, or specific progress information for a particular merit badge.
- A user should have the option to export their merit badge data, as well as import previously exported data.

# Other Requirements
- All data will be stored locally on the mobile device. There is no cloud syncing of data.

# Design decisions
Choices about how the app looks and behaves, made while building it, and why. Technical decisions are in [`ARCHITECTURE.md`](ARCHITECTURE.md#decisions).

| Decision | Choice | Why |
|---|---|---|
| Badge search | Every word of the search must start a word in the badge's name or summary, in any order, ignoring case | Finds a badge from the start of any word ("fit" finds Personal Fitness) without matching inside words, so a short search like "art" isn't flooded with summaries that say "part" or "start" |
| Search result announcements | A line under the search field says how many badges match. Screen readers hear a new count once typing pauses for a second, or straight away after Clear search, and only when it changes | Android 16 deprecates `announceForAccessibility`, and its [behavior changes](https://developer.android.com/about/versions/16/behavior-changes-all) point to live regions instead, "used sparingly". With TalkBack, a count announced on every keystroke was spoken ahead of the key just typed, and held back its echo by 1 to 4 seconds |
| Eagle-required progress | Home counts each Eagle "one of" group, such as Cycling, Hiking and Swimming, once, with the status of its furthest-along badge | Earning any badge in the group meets the requirement |
| Badge progress bar | While a badge is in progress, a bar shows how much of it is done: under its name and Eagle-required line on Badges and Home, with "In progress" still at the row's end, and at the top of Badge detail, under its name. Each top-level requirement counts the same. Within one, each part it needs counts: the sub-requirements it needs (the furthest along, when only some are), its own work, and a fixed-row tracker's rows, such as 8 of 12 weeks. Screen readers hear how much is done with "In progress", such as "40% done. In progress" in TalkBack | "In progress" alone didn't tell a badge just started from one nearly done ([#159](https://github.com/bryancassell/bluecard/issues/159)). Counting only complete top-level requirements would leave the bar still while the scout works through a big one, such as First Aid 3's 17 parts, and counting every part the same would let one big requirement outweigh the rest |
| Requirement list | Badge detail lists only the top-level requirements, one row each: the official number, our one-line summary, "Do N of M" when only some sub-requirements are needed, and how much of its tracker is filled in, such as "8 of 12 weeks", or its totals (Tracker totals), or how many merit badges count toward it (Merit badge requirements). Each row opens the requirement's own page, which lists its sub-requirements the same way | Requirements stay understandable "without extensive scrolling": each page shows one level of the requirement tree |
| Marking a requirement complete | A "Completed" checkbox on the requirement's page, dated today, with the date and notes beside it. Dates after today can't be picked. Rows only open the page. A requirement with sub-requirements is complete once enough of them are, so it has no checkbox, unless it asks for work of its own too (below) | Chosen after using the app, in place of a checkbox on each row ([#103](https://github.com/bryancassell/bluecard/issues/103)). Each part takes a trip to its page, so marking many (Personal Fitness 3 has seven) is slower; the date and notes are optional |
| A requirement's own work | When a requirement with sub-requirements also asks for work of its own, such as Space Exploration 3's rocket launches, its page has a checkbox for that work above its sub-requirements, labeled with our summary of it and dated like any other. The requirement is complete once that's checked and enough sub-requirements are, on the later of their dates. This counts any ask its sub-requirements don't cover, including a closing discussion with the counselor. On every requirement's page, "Do N of M" sits right above the sub-requirements it counts, below the checkbox and "Completed" | Enough sub-requirements alone completed requirements whose main work wasn't done, and the badge with them ([#143](https://github.com/bryancassell/bluecard/issues/143)). Only those requirements get the checkbox: a checkbox on every requirement with sub-requirements would add a trip to the many that only group them. The label says exactly what to check off, where a generic "Completed" would be wrong until the sub-requirements are done. With "Do N of M" under the summary, the checkbox came between the count and the sub-requirements it counts |
| Showing whether a requirement is complete | The row's number sits in a box: outlined while no part of it is complete, then tinted light blue with a blue outline and a half-filled circle on its corner once part of it is done (its own work, a row of its tracker, a badge that counts toward the merit badges it asks for, or a requirement under it at any depth), then filled in Scouting America Blue with a check on its corner once it's complete. Filled in grey, with "Not needed", once a requirement it's part of has enough complete sub-requirements, even if that requirement's own work isn't done yet, and its page says "Not needed" too. Screen readers read "Completed", "In progress", "Not completed" or "Not needed" as the row's state, or "Not recorded" in place of "Not completed" on a badge marked completed on a prior date (below). Every box in a list is as wide as the list's widest number needs at the current font size | A small check beside the chevron was easy to miss ([#123](https://github.com/bryancassell/bluecard/issues/123)). Filled versus outlined stands out without a new color or more width, and a choice the scout didn't pick no longer looks like work left. Boxes of one width keep the summaries after them lined up, even when sibling numbers differ in width, such as `1b(9)` and `1b(10)` ([#131](https://github.com/bryancassell/bluecard/issues/131)). Until the tint, a requirement looked untouched until all of it was done, including one waiting only on its own work, and Badge detail showed nothing of progress below the top level ([#158](https://github.com/bryancassell/bluecard/issues/158), [#151](https://github.com/bryancassell/bluecard/issues/151)). The light blue tint barely stands out from the background, so the half circle tells it from an untouched box by shape, not color alone ([WCAG 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)), and pairs with the check: half done, then done |
| Counting complete sub-requirements | A tinted row also says how many of the sub-requirements it needs are complete: "(2 of 5 complete)", or "Do 2 of 3 (1 of 2 complete)" when only some are needed. It counts toward the number needed and never past it, counts only the requirement's own sub-requirements, and is left out while none of them are complete | Counting toward the number needed says how close the requirement is. A count of "0 of 3" beside a tinted box, when only a requirement further down is complete, would read as nothing done ([#158](https://github.com/bryancassell/bluecard/issues/158)) |
| Unchecking a requirement | Removes its date and keeps its notes. The page remembers the date until it closes or the requirement is cleared, and checking the requirement again there brings the date back | A mistaken tap loses nothing, while stored progress stays simple: a requirement that isn't complete has no date |
| Starting a badge | Recording anything starts it, dated today; it stays started after everything is undone, until the scout clears it | No extra step before recording; clearing a badge is its own action ([#45](https://github.com/bryancassell/bluecard/issues/45)) |
| Ranks | A Ranks button under Merit badges on Home opens Ranks, which lists the seven ranks, Scout through Eagle Scout, in the order they're earned, in the same rows as Badges, with "Earned" where a badge says "Completed". Only the lowest rank not yet earned says "In progress", with its bar, even before anything is recorded for it, so a new scout's Scout rank does. Another rank that isn't earned shows its bar once it's started, without the label. A rank is earned only once the rank below it is, even with all its requirements complete; until then its bar shows how much is done, up to 100%. Each rank opens Rank detail, laid out as Badge detail without the counselor or the Eagle-required label. Under its official link, a rank earned from its requirements says "Earned on <date>", the date its last requirement was completed, or "Earned" if one has no date. A rank whose requirements are all complete but isn't earned says "Earned once Tenderfoot is earned" above Mark earned. Once it's earned, its report can be shared and saved (PDF report) | Ranks are earned in order, so while the scout can record requirements for any rank, only one is next ([#193](https://github.com/bryancassell/bluecard/issues/193)). Scouts say a rank is earned, not completed. Sharing Badges' rows and Badge detail's layout keeps ranks familiar. Without the two lines, a rank earned from its requirements looked like one not started, and a complete rank's full bar didn't say why it wasn't earned ([#211](https://github.com/bryancassell/bluecard/pull/211)) |
| Rank on Home | First on Home, under the name and unit: "Your rank: Tenderfoot", or "You haven't earned a rank yet.", as a heading screen readers can jump to. Under it, the rank in progress, in the same row as on Ranks, with its bar, opening its Rank detail. Once Eagle Scout is earned, only the line shows | Rank is the scout's main standing, and merit badges count toward it, so it comes before them ([#193](https://github.com/bryancassell/bluecard/issues/193)). Like a badge in progress on Home, the row opens straight to what's left to do, and it reads the same as on Ranks |
| Marking a rank earned on a prior date | As for a badge (below), with "Mark earned" and "Earned on <date>". Marking a rank counts every rank below it as earned, with no date of its own: its page says "Counted as earned with Life", with Add date, which marks it earned on the date picked, and its requirements not recorded read "Not recorded". Unmarking the rank undoes what its mark counted | A scout who starts using BlueCard as a Life Scout marks only Life ([#193](https://github.com/bryancassell/bluecard/issues/193)). Worked out rather than stored, so unmarking can't leave a lower rank earned by mistake. Add date gives a lower rank a date of its own, which time in rank, such as Star's months as First Class, counts from |
| Time in rank | Star 1 and 5, Life 1 and 5, and Eagle 1 and 4 ask for months in the rank below. Their page says when the scout becomes eligible, under the summary: "Eligible from Jan 1, 2027, 4 months after earning First Class", from the date the rank below was earned on. Until it's earned, or while it has no date, the page says so instead: "Eligible 4 months after earning First Class, which isn't earned yet", or "…which has no date it was earned on". The line stays once the requirement is checked off, and only the page shows it, not the requirement's row. The scout checks the requirement off, before or after the date | The date is only a guide ([#193](https://github.com/bryancassell/bluecard/issues/193)): a scout who took a position of responsibility after earning the rank below is eligible later, and on Star 5 and Life 5 a leadership project can replace the months |
| Merit badge requirements | Star 3, Life 3 and Eagle 3 ask for merit badges: 6, at least 4 of them Eagle-required, for Star; 11, at least 7 of them Eagle-required, for Life; and 21, including the 13 Eagle-required, for Eagle. Each is complete once the scout has completed enough badges, including badges marked completed on a prior date, on the date there were first enough. So it has no checkbox. Star 3 and Life 3 count every Eagle-required badge, so Hiking and Swimming count as two. Eagle 3 counts an Eagle "one of" group once, as Home does: the group's first badge completed counts, and the others count only toward the 21. The row shows "4 of 6 merit badges" and "2 of 4 Eagle-required". The page shows the same under a "Merit badges" heading, then how many more are needed, such as "Needs 3 more merit badges, 2 of them Eagle-required" or "Needs 2 more Eagle-required merit badges". Below that, it lists every badge completed, in name order, with the date it was completed on and "Eagle-required" at the end of each one that counts as Eagle-required toward it. Each badge opens Badge detail. Badges count toward a rank's bar, but a rank still shows its bar only once it's started or while it's in progress | Counting from badge progress means the scout records each badge once ([#193](https://github.com/bryancassell/bluecard/issues/193)). The two counts alone can mislead: a scout with 5 of 6 badges but 2 of 4 Eagle-required could think one more badge would do, and "Needs" says it takes two, both Eagle-required. Each follows its official wording: Star and Life let the scout "choose any of the merit badges on the required list for Eagle", and Eagle lets them "choose only one" of each either-or choice, counting the rest as electives. Every completed badge counts, so every one is listed, not only the first that were enough. On Eagle 3, a group's other badges aren't labeled Eagle-required, so the labels add up to the count. A badge opens so its date can be fixed. Badges alone don't put a bar on a rank, or one earned badge would put bars on Star, Life and Eagle at once |
| Marking a badge completed on a prior date | A "Mark completed" button on Badge detail, under the official link, while the badge isn't complete. It opens the date picker, at today, and dates after today can't be picked. Marking starts a badge that isn't started, as recording anything does, and keeps what's recorded for it. The badge then shows "Completed on <date>" in place of the button, with "Change date" and "Unmark", above the report buttons. Unmarking keeps the badge started, with what's recorded, and asks nothing: while the page stays open, Mark completed's picker opens at the date just unmarked. The date isn't checked against its requirements' dates. While it's marked, a requirement that's still needed with no part of it done reads "Not recorded" in place of "Not completed", in the report and for screen readers on its row | Lets a scout count badges earned before using BlueCard without entering each requirement ([#41](https://github.com/bryancassell/bluecard/issues/41)). The picker opens straight away because the date is the point: a prior date is rarely today. Not offered once the badge is complete from its requirements, where marking would add nothing. Completion dates are informational, not a formal requirement, and a scout may record a requirement's details after the badge was earned. "Not completed" beside "Completed on" read as a badge complete with nothing done; a requirement with parts recorded keeps "Not completed", since "Not recorded" would contradict the parts listed under it. Remembering the date, as unchecking a requirement does, makes a mistaken Unmark cost two taps without a dialog every time |
| Trackers | Listed on the requirement's page. Each row is filled in on its own page, with a field for each column, and saved with a Save button. A log lists its entries in the order they were added, numbered from 1 ("Session 3"). A fixed-row tracker shows every row ("Week 1" to "Week 12"), filled in or not, and a row keeps its number when another is deleted. A column that asks for a description or a list, such as "What you saw", has a multi-line field like the requirement notes, and the row's summary on the requirement's page shows its line breaks as spaces. Names and short values, such as "Planet", stay on one line | Four or more fields don't fit in a dialog or a table row on a phone once the keyboard is up. Numbered rows match trackers such as a 13-week budget, where each week is its own row. A one-line field scrolls sideways, so the scout saw only a few words of a description, and a list of chores ran together ([#168](https://github.com/bryancassell/bluecard/issues/168)) |
| Save while typing in a tracker row | While the scout types in a row's last field, the page scrolls to keep that field and Save above the keyboard, with Save still under the fields. It does so once the keyboard has opened, so the page can take a second, short scroll after the keyboard settles. When the field grows too tall for both to fit, the page keeps the line being typed in view instead, as it does for the other fields | Save sat partly behind the keyboard once a row's last field could take more than one line ([#172](https://github.com/bryancassell/bluecard/issues/172)). Scrolling keeps the page laid out as before; a bar fixed above the keyboard would have taken room from the fields while typing. Scrolling to Save while the keyboard was still opening left a tall field's line behind the keyboard on a phone. The line being typed matters more than Save, which is a scroll away |
| Completing a fixed-row tracker's requirement | Always inferred once every row is filled in, with no checkbox. A row is filled in once it's saved, even with some of its fields empty, so saving only Family Life 3's 13 week-start dates completes it. Its date starts as when the last row was first saved. Once it's complete, its page shows "Completed on <date>" under "Completed", with Change date and Remove date, as for a checked requirement. Once the date is removed, Add date opens the picker at the date the last row was saved. A date the scout changes or removes stays that way while a row is deleted, and once every row is filled in again; clearing the requirement goes back to the date the last row was saved. A log keeps the checkbox | A fixed-row tracker is a list of parts, like sub-requirements ([#105](https://github.com/bryancassell/bluecard/issues/105)). A field can be empty for good reason, such as a week with no income, and the app doesn't decide which of a requirement's columns it needs ([#115](https://github.com/bryancassell/bluecard/issues/115)). Rows typed in after the work, as when copying a paper log, dated the requirement, and the badge with it, the day they were typed ([#116](https://github.com/bryancassell/bluecard/issues/116)). The tracker's date column isn't used, because most fixed-row trackers have none, such as Personal Management 2a and 2c, and Family Life 3's is the week's start. Deleting a row is often a fix, not undoing the work. Opening Add date at the rows' date gives a removed date a way back without another button; Clear would delete the rows too. A log's total, such as Camping 9a's 20 nights, is only a guide (Tracker totals) |
| Tracker totals | A log whose requirement asks for an amount, such as Star 4's 6 hours of service or Camping 9a's 20 nights, adds that column up against it: "4.5 of 6 hours", and for Life 4 "2 of 3 conservation hours" too. The requirement's row shows its totals in place of how many rows there are, and its page and the PDF report show them under that count. The requirement keeps its checkbox: the totals don't complete it. A total has up to two decimal places, rounded down, with its digits not grouped | The scout sees how far along they are without adding up the rows ([#193](https://github.com/bryancassell/bluecard/issues/193)). On the row, the amount says more than the number of projects. A total is only a guide: a requirement can ask for more than the amount, such as Life 4's Scoutmaster-approved projects, so the scout checks it off. Rounding down means a total never reads "6 of 6 hours" before it's reached. A grouping comma could read as a decimal separator, which the scout can type |
| Requirement notes | On every requirement, including one with sub-requirements, saved with a Save button | The scout decides when notes are saved, and a save that fails is reported right then, not while they're still typing |
| Counselor details | Shown on Badge detail, between the official link and the requirements; edited on a page of their own with a Save button, which closes it once the save succeeds. Tapping the phone or email opens the phone or email app, with no format check | Entered once and read often, so Badge detail stays short; closing only after a successful save shows a failure while the scout can still try again; opening the phone and email apps needs no permissions |
| Unsaved changes on Back | Back asks "Discard changes?" first on a page whose fields differ from what's saved: Tracker entry, a requirement's notes, Edit counselor, and Edit name and unit. It asks even when Save is off, as with a blank name or every field of a saved tracker row emptied. Cancel keeps the page and the edit, and the red Discard closes the page without saving. A requirement's page says it's the notes that aren't saved, as its checkbox and date save straight away | Back discarded edits with no warning ([#99](https://github.com/bryancassell/bluecard/issues/99)). Saving on Back instead would close the page before a failed save could be reported, which Requirement notes and Counselor details avoid, and would leave no way to throw an edit away |
| Clearing a requirement | A "Clear progress" button at the bottom of its page, once anything is recorded for it or a requirement under it. It clears them all; the badge stays started | The scout reads a requirement as including its sub-requirements |
| Clearing a badge | A "Clear progress" button at the bottom of Badge detail, once the badge is started, even with nothing recorded. It clears everything recorded for the badge, including its counselor, and the badge is no longer started. The page stays open and shows the badge's newest requirements | A started badge shows as In progress, and clearing it is the only way back to not started. Staying on the page shows the scout what the clear did, as clearing a requirement does |
| Clearing a rank | As for a badge. When clearing it means other ranks no longer count as earned, because its mark counted them or they were earned in order after it, the dialog names them: "What you recorded for it will be removed, and Scout and Tenderfoot will no longer count as earned." | Ranks are earned in order, so clearing one can change others, which its page doesn't show ([#211](https://github.com/bryancassell/bluecard/pull/211)). Unmarking a rank asks nothing, as for a badge, and the page remembers the date |
| Unsaved notes when clearing | Clear progress also discards an unsaved edit of the requirement's notes, once the clear is saved, and the dialog warns about it first. A clear that fails keeps the edit | Decided after [#133](https://github.com/bryancassell/bluecard/pull/133), where an unsaved edit survived a clear: discarding it made the most sense ([#137](https://github.com/bryancassell/bluecard/pull/137)) |
| Confirming a removal | Deleting a tracker row, clearing progress and discarding unsaved changes ask first, in one shared dialog with Cancel and a red confirm button, the theme's error color. The Delete and Clear progress buttons that open it are red too | Red marks the button that removes what the scout recorded, which can't be undone, so it stands apart from Cancel. Sharing the dialog keeps every removal alike |
| PDF report | "Share report" and "Save report" on Badge detail once the badge is complete, under the official link, and on Rank detail once the rank is earned, under how it's earned, including a rank counted as earned with a rank above it. US Letter pages with the scout, the badge or rank, when it was completed or earned (or "Counted as earned with Life"), its requirements version, a badge's counselor, every requirement of the version at every level (including "Not completed" and "Not needed" ones) with its dates, notes and tracker rows, page numbers and the day it was created. Star 3, Life 3 and Eagle 3 show "4 of 6 merit badges" and "2 of 4 Eagle-required", then every badge completed, in name order, a line each with its date, and "Eagle-required" on each that counts as Eagle-required toward it, as their pages do. A time in rank requirement's eligibility date isn't in it | Scouting America is in the US. A counselor reading it sees the whole badge, including what wasn't done. Page numbers keep printed pages in order, and the date tells an old copy from a new one. A rank is offered its report once it's earned, as a badge once it's complete ([#193](https://github.com/bryancassell/bluecard/issues/193)). Every completed badge is listed, as on the requirement's page, so a report made after a later rank lists that rank's badges too, and their dates tell them apart. The eligibility date is only a guide, and the requirement's own date says when it was done |
| Changing the name and unit number | A "Name and unit" section, first on Data management, with an Edit button. It opens a page like the counselor's: both fields, filled in and still required, and a Save button that closes it once the save succeeds. The keyboard's Done only closes the keyboard, where Onboarding's also saves | Changed rarely, so Home stays as it is, and the page sits with the scout's other data ([#160](https://github.com/bryancassell/bluecard/issues/160)). As on the counselor's page, the scout decides when to save, since saving closes the page |
| Export | Export on Data management saves the name, unit number and all progress to one file where the scout chooses, with the system file picker. It suggests a name with the date, such as "BlueCard export 2026-10-01.json" | The date tells exports apart, and they sort by it. The file picker lets the scout keep it on the phone or in a cloud drive, without storage permissions |
| Import | Replaces all current data (profile and progress), after a warning that says so. The scout can pick any file, and it's checked before the warning, which has a red Replace button. A file that isn't an export, or is from a newer version of the app (including one with badges or requirements this version doesn't have), gets a message saying so. A line break in the name, unit number, a counselor's details or a tracker's one-line text field is imported as a space. "Data imported." confirms an import | Simplest correct behavior; merging is tracked in [#28](https://github.com/bryancassell/bluecard/issues/28). Checking first means the scout is never asked to confirm a file that can't be imported ([#46](https://github.com/bryancassell/bluecard/issues/46)). An export copied to the phone some other way may not be labeled as JSON, and the file picker won't let the scout choose a file it filters out. Data management itself doesn't change after an import, so a message confirms it. A one-line field never shows a line break, so a space keeps the text the scout sees, and an export saved before those fields replaced pasted line breaks still imports ([#156](https://github.com/bryancassell/bluecard/issues/156)) |
| Clearing all progress | A "Clear all progress" section, last on Data management, with a red "Clear all" button, disabled until a badge or rank is started. It asks first, then clears every badge's and rank's progress, counselors included, and keeps the name and unit number. "Progress cleared." confirms it, and a clear that fails says "Couldn't save. Try again.", as on the badge and requirement pages | Last and red, so it isn't tapped by mistake. Disabled rather than hidden, unlike the other clears' buttons, so the scout can see where clearing everything lives. A message confirms it, as for an import ([#45](https://github.com/bryancassell/bluecard/issues/45)) |
| Damaged progress | When the progress saved on the phone is found damaged, BlueCard starts over without it and says so in a dialog over whichever page is open: "Your progress couldn't be read", that the name and unit number are kept, and that a file exported before can be imported from Data management. Only OK closes it, so it shows again at the next launch until the scout taps it. When the damage is found while the scout is using the app, the dialog shows over the page's "Couldn't load your data" message, and the app closes the next time it reads or saves progress, such as when it's reopened, then starts over. The dialog doesn't mention Android's backup | A scout's records may cover years of work, so they're never lost without the scout knowing ([#70](https://github.com/bryancassell/bluecard/issues/70)). Damage is rare, so closing the app once is simpler than recovering while it's open. Restoring Android's backup means reinstalling BlueCard, which deletes what's on the phone, and works only if the nightly backup ran before the damage and hasn't run since, so it isn't suggested |
| Switching requirement versions | Starts the badge's requirement progress fresh, after a confirmation; counselor details stay | Requirement numbers can mean different things in different versions, so entries aren't attached to the wrong requirement; carrying progress over is tracked in [#29](https://github.com/bryancassell/bluecard/issues/29) |
| Requirement changes | Shipped with regular app updates, with no urgency or monitoring process | The app doesn't need to reflect Scouting America's changes immediately.
