# Overview
I want to build an Android mobile app that will allow Scouting America scouts to track and record their progress in earning merit badges. 

# Key User Journeys
- On first app launch the user should be prompted for their name and unit number.
- On subsequent app launches the user should land on a home page that displays their name and a summary of their merit badge progress.
- A user should be able to browse a list of all current Scouting America merit badges.
- A user should be able to search for a specific merit badge by name or description.
- When a merit badge is selected the user should be given a page that briefly describes the merit badge and allows the user to record their progress towards completion.
  - This page should begin with a brief description of the merit badge and any relevant information, such as whether it is eagle required.
  - This page should give the user the ability to enter their merit badge counselor's name and contact information.
  - This page should give the user a brief description of each requirement for the merit badge as well as the ability to record all relevant data necessary to satisfy the progress against that requirement.
  - This page should be easy to navigate on a mobile device, and the user should be able to understand the full set of requirements without extensive scrolling. If any part of the merit badge requires large trackers or detailed information the user should have the option to click into a sub-page for those requirements.
  - Where possible, the brief descriptions of requirements should link to the full, official, Scouting America documentation for the relevant requirement.
  - When recording progress on a merit badge requirement the user should have the option to include a date on which the requirement was completed.
  - When recording progress on a merit badge the user should have the option to add notes about that requirement.
  - When a merit badge is completed the user should have the ability to generate a report in PDF format that reflects the entirety of the data they have recorded for that merit badge, and to save and/or share that report with standard Android save and share features.
  - This page should allow the user to mark a merit badge as completed on a prior date without entering specific data for each requirement.
  - Scouting America updates merit badge requirements over time, usually each January 1. By default, a merit badge should use the newest version of its requirements.
  - The user should be able to select the previous version of a merit badge's requirements instead, when the app has one, for example if they started working on the badge before a change.
  - The first release of the app includes only each merit badge's current requirements. From then on, the app keeps every version of the requirements it has shipped, so existing users can keep working on the version they started.
  - When an app update brings newer requirements for a merit badge the user has already started, the badge should stay on the version the user was using, so their recorded progress still matches its requirements. The user should be able to switch that badge to the newest version themselves.
- A user should have the option to clear all merit badge data, all progress for a specific merit badge, or specific progress information for a particular merit badge.
- A user should have the option to export their merit badge data, as well as import previously exported data.

# Other Requirements
- All data will be stored locally on the mobile device. There is no cloud syncing of data.

# Design decisions
Choices about how the app looks and behaves, made while building it, and why. Technical decisions are in [`ARCHITECTURE.md`](ARCHITECTURE.md#decisions).

| Decision | Choice | Why |
|---|---|---|
| Badge search | Every word of the search must start a word in the badge's name or summary, in any order, ignoring case | Finds a badge from the start of any word ("fit" finds Personal Fitness) without matching inside words, so a short search like "art" isn't flooded with summaries that say "part" or "start" |
| Search result announcements | A line under the search field says how many badges match. Screen readers hear a new count once typing pauses for a second, or straight away after Clear search, and only when it changes | Android 16 deprecates `announceForAccessibility`, and its [behavior changes](https://developer.android.com/about/versions/16/behavior-changes-all) point to live regions instead, "used sparingly". With TalkBack, a count announced on every keystroke was spoken ahead of the key just typed, and held back its echo by 1 to 4 seconds |
| Eagle-required progress | Home counts each Eagle "one of" group, such as Cycling, Hiking and Swimming, once, with the status of its furthest-along badge | Earning any badge in the group meets the requirement |
| Requirement list | Badge detail lists only the top-level requirements, one row each: the official number, our one-line summary, "Do N of M" when only some sub-requirements are needed, and how much of its tracker is filled in, such as "8 of 12 weeks". Each row opens the requirement's own page, which lists its sub-requirements the same way | Requirements stay understandable "without extensive scrolling": each page shows one level of the requirement tree |
| Marking a requirement complete | A "Completed" checkbox on the requirement's page, dated today, with the date and notes beside it. Dates after today can't be picked. Rows only open the page. A requirement with sub-requirements is complete once enough of them are, so it has no checkbox, unless it asks for work of its own too (below) | Chosen after using the app, in place of a checkbox on each row ([#103](https://github.com/bryancassell/bluecard/issues/103)). Each part takes a trip to its page, so marking many (Personal Fitness 3 has seven) is slower; the date and notes are optional |
| A requirement's own work | When a requirement with sub-requirements also asks for work of its own, such as Space Exploration 3's rocket launches, its page has a checkbox for that work above its sub-requirements, labeled with our summary of it and dated like any other. The requirement is complete once that's checked and enough sub-requirements are, on the later of their dates. This counts any ask its sub-requirements don't cover, including a closing discussion with the counselor. On every requirement's page, "Do N of M" sits right above the sub-requirements it counts, below the checkbox and "Completed" | Enough sub-requirements alone completed requirements whose main work wasn't done, and the badge with them ([#143](https://github.com/bryancassell/bluecard/issues/143)). Only those requirements get the checkbox: a checkbox on every requirement with sub-requirements would add a trip to the many that only group them. The label says exactly what to check off, where a generic "Completed" would be wrong until the sub-requirements are done. With "Do N of M" under the summary, the checkbox came between the count and the sub-requirements it counts |
| Showing whether a requirement is complete | The row's number sits in a box: outlined until it's complete, then filled in Scouting America Blue with a check on its corner. Filled in grey, with "Not needed", once a requirement it's part of is complete, and its page says "Not needed" too. Screen readers read "Completed", "Not completed" or "Not needed" as the row's state. Every box in a list is as wide as the list's widest number needs at the current font size | A small check beside the chevron was easy to miss ([#123](https://github.com/bryancassell/bluecard/issues/123)). Filled versus outlined stands out without a new color or more width, and a choice the scout didn't pick no longer looks like work left. Boxes of one width keep the summaries after them lined up, even when sibling numbers differ in width, such as `1b(9)` and `1b(10)` ([#131](https://github.com/bryancassell/bluecard/issues/131)) |
| Unchecking a requirement | Removes its date and keeps its notes. The page remembers the date until it closes or the requirement is cleared, and checking the requirement again there brings the date back | A mistaken tap loses nothing, while stored progress stays simple: a requirement that isn't complete has no date |
| Starting a badge | Recording anything starts it, dated today; it stays started after everything is undone, until the scout clears it | No extra step before recording; clearing a badge is its own action ([#45](https://github.com/bryancassell/bluecard/issues/45)) |
| Trackers | Listed on the requirement's page. Each row is filled in on its own page, with a field for each column, and saved with a Save button. A log lists its entries in the order they were added, numbered from 1 ("Session 3"). A fixed-row tracker shows every row ("Week 1" to "Week 12"), filled in or not, and a row keeps its number when another is deleted | Four or more fields don't fit in a dialog or a table row on a phone once the keyboard is up. Numbered rows match trackers such as a 13-week budget, where each week is its own row |
| Completing a fixed-row tracker's requirement | Always inferred once every row is filled in, with no checkbox. Its date is when the last row was first saved. A log keeps the checkbox | A fixed-row tracker is a list of parts, like sub-requirements ([#105](https://github.com/bryancassell/bluecard/issues/105)). The tracker's date column isn't used, because Personal Management 2a and 2c have none. A log has no target in the catalog, such as Camping 9a's 20 nights |
| Requirement notes | On every requirement, including one with sub-requirements, saved with a Save button | The scout decides when notes are saved, and a save that fails is reported right then, not while they're still typing |
| Counselor details | Shown on Badge detail, between the official link and the requirements; edited on a page of their own with a Save button, which closes it once the save succeeds. Tapping the phone or email opens the phone or email app, with no format check | Entered once and read often, so Badge detail stays short; closing only after a successful save shows a failure while the scout can still try again; opening the phone and email apps needs no permissions |
| Clearing a requirement | A "Clear progress" button at the bottom of its page, once anything is recorded for it or a requirement under it. It clears them all; the badge stays started | The scout reads a requirement as including its sub-requirements |
| Unsaved notes when clearing | Clear progress also discards an unsaved edit of the requirement's notes, once the clear is saved, and the dialog warns about it first. A clear that fails keeps the edit | Decided after [#133](https://github.com/bryancassell/bluecard/pull/133), where an unsaved edit survived a clear: discarding it made the most sense ([#137](https://github.com/bryancassell/bluecard/pull/137)) |
| Confirming a removal | Deleting a tracker row and clearing progress ask first, in one shared dialog with Cancel and a red confirm button, the theme's error color. The Delete and Clear progress buttons that open it are red too | Red marks the button that removes what the scout recorded, which can't be undone, so it stands apart from Cancel. Sharing the dialog keeps every removal alike |
| PDF report | "Share report" and "Save report" on Badge detail once the badge is complete, under the official link. US Letter pages with the scout, the badge, its requirements version, the counselor, every requirement of the version at every level (including "Not completed" and "Not needed" ones) with its dates, notes and tracker rows, page numbers and the day it was created | Scouting America is in the US. A counselor reading it sees the whole badge, including what wasn't done. Page numbers keep printed pages in order, and the date tells an old copy from a new one |
| Import | Replaces all current data (profile and progress), after a warning that says so | Simplest correct behavior; merging is tracked in [#28](https://github.com/bryancassell/bluecard/issues/28) |
| Switching requirement versions | Starts the badge's requirement progress fresh, after a confirmation; counselor details stay | Requirement numbers can mean different things in different versions, so entries aren't attached to the wrong requirement; carrying progress over is tracked in [#29](https://github.com/bryancassell/bluecard/issues/29) |
| Requirement changes | Shipped with regular app updates, with no urgency or monitoring process | The app doesn't need to reflect Scouting America's changes immediately. Scouts who already started may keep the previous requirements anyway. Until an update ships, a scout starting a changed badge sees the previous requirements in the app; the linked official page has the current ones |
| Page transitions | Pages slide the full width of the screen, side by side, in 375 ms. A back swipe from either edge doesn't move the pages; once released, it plays Back's slide. Onboarding and the rest of the app crossfade when one replaces the other, since neither is a page of the other | Navigation 3's defaults (a 700 ms crossfade, and a 70% shrink on the back gesture) looked strange ([#104](https://github.com/bryancassell/bluecard/issues/104)). Material 3's [transition patterns](https://m3.material.io/styles/motion/transitions/transition-patterns) say "Both Android and iOS should use platform defaults for forward and backward navigation" between "screens at consecutive levels of hierarchy", and "Sliding content the full width of the screen is excessive for a high frequency transition." The platform's slides move 96dp and fade, but on a Pixel 9 opening a page felt too short, the back swipe's fade looked bad, and a swipe from the right edge that didn't slide the page looked broken. When the pages followed the finger, a released swipe finished slowly beside opening a page, so the swipe gives up predictive back's peek at the page underneath |
| Colors | The merit badge blue card's colors, the same on every phone: none taken from the wallpaper, and the light scheme in dark mode too, until the app has a dark one ([#108](https://github.com/bryancassell/bluecard/issues/108)). Readability comes before matching the card exactly: every text color meets WCAG AA (4.5:1) | The app takes its look from the blue card |
| Links to scouting.org | Link each badge to its official page | The PRD asks for links. Scouting America's [terms of use](https://www.scouting.org/legal/terms-and-conditions/), read literally, restrict linking without permission; resolve before release ([#26](https://github.com/bryancassell/bluecard/issues/26)) |
| Official wording | Use Scouting America's terms, such as "Merit Badge" and "Eagle Scout", and official badge names | Clearest for scouts. These are Scouting America [trademarks](https://licensingbsa.org/trademarks/); resolve before release ([#27](https://github.com/bryancassell/bluecard/issues/27)) |
